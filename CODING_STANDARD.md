# Стандарт кодування проєкту ShopOrders

Проєкт: ShopOrders (варіант № 1), C# 12, .NET 8. Автор: Шевченко Р. В., група 472.
Версія стандарту: 1.0.0. Кожен пункт сформульовано так, щоб рецензент міг однозначно сказати «дотримано» або «порушено».

## 1. Сфера дії, рівні обов'язковості, глосарій

### 1.1. Сфера дії

- **Поширюється на:** бібліотеки логіки `ShopOrders.Core` і `ShopOrders.Domain`, консольний застосунок `ShopOrders.App`, проєкт тестів `ShopOrders.Tests`, а також файли `.editorconfig`, `Directory.Build.props`, `*.csproj`.
- **Не поширюється на:** згенерований код (`obj/`, `bin/`, `*.g.cs`) і гілки-пісочниці (`sandbox/*`).
- **Суворіші вимоги до бібліотек логіки** (`Core`, `Domain`): заборона `double`/`float`, заборона `DateTime.Now`, округлення лише з явним режимом (X-02, X-03, D-17). Консольному застосунку й тестам ці заборони не потрібні: там немає грошової логіки.
- **Діє з** 14.11.2026. **Власник:** автор (Шевченко Р. В.), зміни за порядком з розділу 7.3.
- **Мова:** ідентифікатори англійською, коментарі й XML-документація українською (C-12).
- **Мінімальні налаштування рішення:** `Nullable` і `ImplicitUsings` увімкнено для всіх проєктів через `Directory.Build.props` (D-09, п. 6.3).

### 1.2. Рівні обов'язковості

| Рівень | Значення | Наслідок порушення | Рівень у `.editorconfig` |
| --- | --- | --- | --- |
| ОБОВ'ЯЗКОВО | виконують завжди | збірка падає або зміни не приймають | `error` |
| РЕКОМЕНДОВАНО | виконують, якщо немає вагомої причини інакше | зауваження на огляді, причину відступу пишуть у коментарі | `suggestion` |
| ДОПУСКАЄТЬСЯ | обидва варіанти прийнятні | зауваження не роблять | `silent` або `none` |
| ЗАБОРОНЕНО | конструкція в проєкті не вживається | збірка або коміт падає | `error` (RS0030, SA1124, `check-style.sh`) |

Розподіл правил за рівнями: ОБОВ'ЯЗКОВО — 48 із 94 (близько 51 %), РЕКОМЕНДОВАНО — 39, ДОПУСКАЄТЬСЯ — 1, ЗАБОРОНЕНО — 6. Переважна більшість правил рівня ОБОВ'ЯЗКОВО перевіряється машиною, правила без машинної перевірки перевіряє чекліст.

### 1.3. Нумерація правил

N — іменування; F — форматування й структура файлу; C — коментарі й документація; D — дані й типи; S — керуючі конструкції й складність; A — машинна частина; X — правила предметної області (суми й знижки). На огляді пишуть «порушено N-07», а не «мені не подобається».

### 1.4. Шаблон запису правила

Правила записані таблицями: колонки «Правило» (формулювання), «Рівень», «Обґрунтування», «Перевірка». Приклад «порушення / дотримання» для ключових правил наведено парами «ПОГАНО / ДОБРЕ» після таблиці. Поле «Перевірка» є в кожного правила. Способи: аналізатор (із кодом діагностики), `check-style.sh`, чекліст (`docs/CHECKLIST.md`), тест, компілятор.

### 1.5. Глосарій предметної області

Один термін предметної області має один ідентифікатор. Пошук по коду за `Customer` має знаходити все, що стосується покупця.

| Поняття | Ідентифікатор | Пояснення |
| --- | --- | --- |
| замовлення | `Order` | документ, який створює покупець |
| позиція замовлення | `OrderLine` | товар у замовленні з кількістю та ціною |
| покупець | `Customer` | особа, яка оформлює замовлення; слова `Client`, `Buyer`, `User` не вживаємо |
| товар | `Product` | одиниця каталогу з артикулом і ціною |
| артикул | `Sku` | унікальний код товару |
| кількість | `Quantity` | кількість одиниць товару в позиції |
| ціна за одиницю | `UnitPrice` | ціна одного товару в гривнях, `decimal` |
| проміжна сума | `Subtotal` | сума позицій до знижки |
| знижка | `Discount` | сума, віднімана від проміжної суми |
| ставка знижки | `DiscountRate` | частка від 0 до 1, `decimal` |
| рівень знижки | `DiscountTier` | перелічення: `None`, `Bronze`, `Silver`, `Gold` |
| постійний покупець | `IsRegular` | ознака покупця, що дає право на знижку |
| підсумок | `Total` | сума до сплати після знижки й округлення |
| статус замовлення | `OrderStatus` | стан у життєвому циклі замовлення |
| документ | `Document` | узагальнення, з яким працюють калькулятор і звіт |
| звіт | `Report` | текстове подання результату розрахунку |
| створено / оплачено | `CreatedAt` / `PaidAt` | моменти часу, `DateTimeOffset` |

Історичний виняток: тип `ClientInfo` порушує правило про `Customer`; перейменування відкладено, див. DR-003 у `docs/DECISIONS.md`.

### 2.2. Приклади «погано / добре»

```csharp
// ПОГАНО (N-07, N-10, D-06)
public decimal Calc(List<OrderLine> l, int t)
{
    decimal s = 0;
    foreach (var x in l) s += x.UnitPrice * x.Quantity;
    if (t == 1) s = s * 0.95m;
    return s;
}

// ДОБРЕ
public decimal CalculateTotal(IReadOnlyList<OrderLine> lines, DiscountTier tier)
{
    decimal subtotal = 0m;
    foreach (OrderLine line in lines)
    {
        subtotal += line.UnitPrice * line.Quantity;
    }

    return ApplyDiscount(subtotal, tier);
}
```

`Calc` не каже, що рахує; `l` і `t` неможливо знайти пошуком; `t == 1` — магічне число, зміст якого знає лише автор. `DiscountTier` не дозволяє передати випадкове число.

```csharp
// ПОГАНО (N-09)
public bool Flag { get; set; }
public bool Delete { get; set; }

// ДОБРЕ
public bool IsPaid { get; private set; }
public bool CanBeCancelled => Status == OrderStatus.New;
```

`Delete` читається як команда, тож ім'я бреше про вид члена; `Flag` не каже, про що прапорець.

```csharp
// ПОГАНО (N-04)
private decimal total;

// ДОБРЕ
private decimal _total;
```

Поле без префікса плутають із локальною змінною, і читач змушений повертатися до початку класу.

```csharp
// ПОГАНО (N-03)
public interface OrderRepository { }

// ДОБРЕ
public interface IOrderRepository { }
```

Без `I` не видно, що тип є контрактом, а не реалізацією.

```csharp
// ПОГАНО (N-20)
var data = Load();
var temp = data.Sum(x => x.Amount);

// ДОБРЕ
IReadOnlyList<OrderLine> lines = LoadLines();
decimal subtotal = lines.Sum(line => line.UnitPrice * line.Quantity);
```

`data` і `temp` годяться для чого завгодно, а значить, ні про що не повідомляють.

```csharp
// ПОГАНО (N-21)
public int Kilkist { get; set; }
public decimal Zamovlennya { get; set; }

// ДОБРЕ
public int Quantity { get; set; }
public decimal Total { get; set; }
```

Транслітерація ламає глосарій: пошук за `Quantity` не знайде `Kilkist`.

```csharp
// ПОГАНО (N-22)
string strCustomerName;
int iLineCount;

// ДОБРЕ
string customerName;
int lineCount;
```

Тип дублюється в імені й застаріває при зміні типу, а компілятор і IDE його й так показують.

```csharp
// ПОГАНО (N-23)
decimal calcOrdTot(Order o) { ... }

// ДОБРЕ
decimal CalculateOrderTotal(Order order) { ... }
```

Скорочення `calcOrdTot` розшифровує кожен по-своєму, а пошук за `Total` його не знаходить.

```csharp
// ПОГАНО (N-24)
public void SaveAndSendReceipt(Order order) { ... }

// ДОБРЕ
public void Save(Order order) { ... }
public void SendReceipt(Order order) { ... }
```

«And» у назві означає два обов'язки: зміна одного зламає інше, а тест потребує обох залежностей.

```csharp
// ПОГАНО (N-25, N-26)
public static class OrderHelper
{
    public static decimal Calculate2(Order order) { ... }
}

// ДОБРЕ
public sealed class OrderTotalCalculator
{
    public decimal Calculate(Order order) { ... }
}
```

`Helper` стає смітником для всього, що не знайшло місця; `2` означає, що ніхто не знає, чим друга версія відрізняється від першої.

```csharp
// ПОГАНО (N-27)
public decimal GetTotal(Order order)
{
    order.Status = OrderStatus.Calculated;
    return order.Lines.Sum(l => l.UnitPrice * l.Quantity);
}

// ДОБРЕ
public decimal CalculateTotal(Order order)
{
    return order.Lines.Sum(line => line.UnitPrice * line.Quantity);
}
```

`Get...` обіцяє запит без побічних ефектів, а метод змінює стан замовлення: помилка проявиться десь далеко від виклику.

### 3.3. Приклади «погано / добре»

```csharp
// ПОГАНО (C-01, C-02, C-03)
// цикл по рядках
foreach (var l in lines)
{
    // додаємо до суми
    total += l.UnitPrice * l.Quantity;
}

// if (customer.IsRegular) total -= total * 0.05m;

// ДОБРЕ
foreach (OrderLine line in lines)
{
    total += line.UnitPrice * line.Quantity;
}

// Знижку рахуємо від підсумку, а не по рядках: інакше копійчані
// заокруглення розходяться із сумою в чеку (X-05).
total = ApplyDiscount(total, customer.IsRegular);
```

Перший варіант переказує код, а закоментований рядок конкурує з робочим кодом за право бути істиною. У другому коментар пояснює вибір, який інакше хтось «виправить».

```csharp
// ПОГАНО (C-06)
// TODO: підтримати купони

// ДОБРЕ
// TODO(RS, #14): підтримати купони, запит у реєстрі завдань
```

Безіменне TODO не має виконавця й терміну, тому лишається в коді назавжди.

```csharp
// ПОГАНО (C-08)
public decimal TotalOf(Order order)

// ДОБРЕ
/// <summary>
/// Обчислює підсумок замовлення з урахуванням знижки.
/// Не змінює стан замовлення.
/// </summary>
/// <param name="order">Замовлення з непорожнім списком позицій.</param>
/// <returns>Сума в гривнях, округлена до копійок.</returns>
/// <exception cref="ArgumentException">Список позицій порожній.</exception>
public decimal TotalOf(Order order)
```

Без документації контракт доводиться відновлювати з тіла методу, зокрема що відбувається з порожнім списком.

```csharp
// ПОГАНО (A-05)
#pragma warning disable CA1062
public void Place(Order order) { ... }

// ДОБРЕ
[SuppressMessage(
    "Design",
    "CA1062:Validate arguments of public methods",
    Justification = "Аргумент перевіряє фабрика OrderFactory")]
public void Place(Order order) { ... }
```

`#pragma` у коді не залишає слідів у перевірках і легко охоплює більше, ніж задумано; атрибут вимагає письмової причини.

### 4.3. Акцент варіанта: суми й знижки

| ID | Правило | Рівень | Обґрунтування | Перевірка |
| --- | --- | --- | --- | --- |
| X-01 | Сума, ціна, знижка — `decimal`; літерал із суфіксом `m` | ОБОВ'ЯЗКОВО | десятковий дріб без похибки подвійної точності; без `m` літерал має тип `double` | компілятор (CS0664, CS0019), чекліст |
| X-02 | `double` і `float` у бібліотеках логіки заборонені | ЗАБОРОНЕНО | у `double` `0.1 + 0.2` не дорівнює `0.3`, і сума розходиться із чеком | `check-style.sh` (ключові слова `double`, `float`), `BannedSymbols.Domain.txt` (типи `Double`, `Single`) |
| X-03 | Округлення лише `Math.Round(x, 2, MidpointRounding.AwayFromZero)` | ОБОВ'ЯЗКОВО | за замовчуванням C# округлює до парного, а каса — від нуля | `BannedSymbols.Domain.txt` (перевантаження без режиму), RS0030 `error` |
| X-04 | Округлюють один раз, на підсумку документа | ОБОВ'ЯЗКОВО | округлення кожного рядка дає суму, що не збігається з підсумком | чекліст, тест |
| X-05 | Знижку рахують від підсумку, а не по рядках; ставку беруть з іменованої константи або `DiscountTier` | ОБОВ'ЯЗКОВО | знижка по рядках накопичує копійчані розходження | чекліст, тест |

```csharp
// ПОГАНО (X-01, X-02, X-03, X-04, D-06)
double price = 199.99;
double total = price * 3;
total = total - total * 0.1;
if (total == 539.97) { ... }

// ДОБРЕ
const decimal RegularDiscountRate = 0.10m;

decimal price = 199.99m;
decimal subtotal = price * 3;
decimal discount = subtotal * RegularDiscountRate;
decimal total = Math.Round(subtotal - discount, 2, MidpointRounding.AwayFromZero);
```

У `double` порівняння `== 539.97` не спрацьовує через похибку представлення; `0.1` — магічне число; округлення відсутнє. Правильна версія округлює один раз і дає точне значення.

```csharp
// ПОГАНО (D-17)
public bool IsExpired() => DateTime.Now > _dueDate;

// ДОБРЕ
public bool IsExpiredOn(DateOnly today) => today >= _dueDate;
```

Прихований годинник унеможливлює тест: результат залежить від моменту запуску. Явний параметр робить метод чистою функцією.

```csharp
// ПОГАНО (D-06)
if (order.Total > 1000m) { discount = 0.15m; }

// ДОБРЕ
private const decimal GoldThreshold = 1000m;
private const decimal GoldDiscountRate = 0.15m;
...
if (order.Total > GoldThreshold) { discount = GoldDiscountRate; }
```

Числа `1000` і `0.15` без імені не пояснюють, звідки вони; змінюючи поріг, легко пропустити друге входження.

```csharp
// ПОГАНО (D-12)
public string Status { get; set; } // "New", "Paid", "Shiped"

// ДОБРЕ
public OrderStatus Status { get; private set; }
```

Рядок приймає друкарську помилку (`Shiped`), яку знайдуть лише в експлуатації; перелічення робить такі значення неможливими.

```csharp
// ПОГАНО (X-03)
decimal total = Math.Round(subtotal - discount, 2);

// ДОБРЕ
decimal total = Math.Round(subtotal - discount, 2, MidpointRounding.AwayFromZero);
```

Без режиму 2,675 і 2,665 округляться в різні боки («до парного»), а касовий апарат округлить обидва вгору.

### 5.3. Приклади «погано / добре»

```csharp
// ПОГАНО (S-01, S-03)
public decimal TotalOf(Order order)
{
    if (order != null)
    {
        if (order.Lines != null)
        {
            if (order.Lines.Count > 0)
            {
                decimal s = 0m;
                foreach (var l in order.Lines) s += l.UnitPrice * l.Quantity;
                return s;
            }
        }
    }
    return 0;
}

// ДОБРЕ
public decimal TotalOf(Order order)
{
    ArgumentNullException.ThrowIfNull(order);

    decimal sum = 0m;
    foreach (OrderLine line in order.Lines)
    {
        sum += line.UnitPrice * line.Quantity;
    }

    return sum;
}
```

Вкладеність упала з чотирьох до двох; `null` замовлення став винятком замість мовчазного нуля, який проявиться як розбіжність у звіті.

```csharp
// ПОГАНО (S-04, D-06)
decimal rate;
if (tier == 1) rate = 0m;
else if (tier == 2) rate = 0.05m;
else rate = 0m;

// ДОБРЕ
decimal rate = tier switch
{
    DiscountTier.None => 0m,
    DiscountTier.Bronze => 0.05m,
    DiscountTier.Silver => 0.10m,
    DiscountTier.Gold => 0.15m,
    _ => throw new ArgumentOutOfRangeException(nameof(tier)),
};
```

Компілятор не дозволить мовчки забути гілку, а ланцюг стає таблицею, яку читають по рядках.

```csharp
// ПОГАНО (S-08, S-09)
if (order.Status == OrderStatus.New && order.Lines.Count > 0
    && customer.IsRegular == true && order.Total > 500m) { ... }

// ДОБРЕ
bool qualifiesForRegularDiscount =
    order.Status == OrderStatus.New
    && order.Lines.Count > 0
    && customer.IsRegular
    && order.Total > MinTotalForDiscount;

if (qualifiesForRegularDiscount) { ... }
```

Іменована змінна пояснює, навіщо чотири умови, і її можна перевірити окремо; `== true` нічого не додає.

## 6. Машинна частина: `.editorconfig` і аналізатори

### 6.1. Принципи

- Рівень у `.editorconfig` дорівнює рівню обов'язковості: ОБОВ'ЯЗКОВО → `error`, РЕКОМЕНДОВАНО → `suggestion`, ДОПУСКАЄТЬСЯ → `silent` або правило не вмикається (A-07). Через `TreatWarningsAsErrors` рівня `warning` у проєкті немає: будь-яке попередження стало б помилкою.
- Придушувати дозволено лише у `.editorconfig` з коментарем-обґрунтуванням або атрибутом `SuppressMessage` з непорожнім `Justification`. Директива `#pragma warning disable` у коді заборонена (A-05).

| ID | Правило | Рівень | Обґрунтування | Перевірка |
| --- | --- | --- | --- | --- |
| A-01 | У корені репозиторію є `.editorconfig` з `root = true` | ОБОВ'ЯЗКОВО | один набір правил для всіх проєктів і редакторів | `dotnet format --verify-no-changes` |

### 6.4. Властивості `Directory.Build.props`

- `LangVersion` — фіксує версію мови C# 12, щоб збірка не залежала від версії SDK.
- `Nullable` — вмикає аналіз посилань, що можуть бути `null` (D-09).
- `ImplicitUsings` — додає типові `using` до кожного проєкту.
- `TreatWarningsAsErrors` — кожне попередження збірки є помилкою.
- `AnalysisMode` — вмикає набір правил якості коду `Recommended`.
- `EnforceCodeStyleInBuild` — правила `IDE*` з `.editorconfig` діють під час `dotnet build`, а не лише в редакторі.
- `GenerateDocumentationFile` — вмикає перевірку CS1591 та IDE0005.

### 6.5. Команди перевірки перед комітом

- `dotnet format --verify-no-changes` — повертає помилку, якщо форматування відрізняється від правил `.editorconfig`.
- `dotnet build -warnaserror` — будь-яке попередження аналізаторів зупиняє збірку.
- `bash tools/check-style.sh` — `double` і `float` у бібліотеках логіки (RS0030 не бачить ключових слів `double`, `float`, див. DR-004), довжина рядка, `#region`, `#pragma`, формат `TODO`, закоментований код, `goto`, порівняння з `true`/`false`, розмір файлу.

### 6.6. Доказ роботи механізму

Місце для знімків: навмисне порушення (`DateTime.Now` у новому файлі `ShopOrders.Core`), вивід `dotnet build` з помилкою RS0030, видалення файлу, вивід `dotnet build` з `Build succeeded`; окремо вивід `check-style.sh` із `double` у `Core` (X-02). Матеріали лежать у `docs/sr1/before.txt` і `docs/sr1/after.txt`.

### 7.2. Порівняння з публічними стандартами

Таблиця складена за пам'яттю про ці настанови; перед захистом її слід звірити з поточними версіями джерел, особливо комірки dotnet/runtime.

#### Відступи від обох джерел

1. **Дужки для одного оператора.** Ми вимагаємо фігурні дужки навіть для одного оператора, хоча настанови dotnet/runtime це пом'якшують. Причина: у навчальному проєкті зміни вносять швидко й часто, а найпоширеніша помилка початківця — додати другий оператор під `if` без дужок. Ціна правила — один зайвий рядок; ціна помилки — дефект, якого не видно під час читання.
2. **Довжина рядка 100.** Жодне з джерел не задає межі, а ми ставимо жорстку. Причина: порівняння версій у двох колонках на екрані 1920 px дає близько 105 символів, і довший рядок змушує прокручувати. Ціна правила — інколи розрив виразу; ціна відсутності — нечитний diff у кожному огляді.
3. **Статичне поле з `_` без `s_`.** dotnet/runtime додає `s_` для статичних полів. Ми цього не робимо, бо в нашому коді статичних приватних полів мало, і окреме правило стоїть витрат на запам'ятовування. Ціна: статичність не видна з імені; вона видна з оголошення біля поля.
4. **Рівень `error` для `.editorconfig`.** Обидва джерела не пропонують зупиняти збірку через стиль. Ми зупиняємо, бо стандарт без примусу в навчальному проєкті живе до першого авралу, а `dotnet format` у хуку дає швидкий зворотний зв'язок.

### 7.3. Порядок внесення змін до стандарту

1. Запропонувати зміну може будь-хто з команди через запит на злиття (pull request) у файл `CODING_STANDARD.md`.
2. Пропозиція містить: правило за шаблоном, обґрунтування, приклад «погано / добре», спосіб машинної перевірки, оцінку вартості приведення наявного коду (кількість файлів).
3. Рішення ухвалює власник стандарту після обговорення в запиті на злиття за принципом: правило приймають, якщо його вартість менша за зекономлений час або кількість помилок; сумнів трактується проти нового правила.
4. Рішення фіксують записом у `docs/DECISIONS.md` із номером (DR-NNN) і датою.
5. Версіювання семантичне: нове правило або зниження рівня — мінорна версія; підвищення рівня правила чи перейменування категорії — старша версія; уточнення тексту — патч.
6. Перехідний період: наявний код не переписують одномоментно, діє правило бойскаута: файл, якого торкнулися, лишають чистішим, ніж він був. Борг за новим правилом погашають протягом 30 днів від набрання ним чинності; рівень `error` вмикають лише після погашення.
7. Скасування шкідливого правила: будь-хто пропонує скасування в тому ж порядку з посиланням на інцидент або дефект; скасування записують у журнал із полем «замінює DR-NNN».
